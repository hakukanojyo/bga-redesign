# 0012. 資料模型的原則

- 狀態：已採用
- 日期：2026-11-05

## 背景

畫面開始要接資料。PRD「找遊戲到加入牌桌」v0.3、產品規則 v0.3 定好了要顯示什麼；第一階段用假資料（[0005](0005-fake-api-layer.md)），第二階段換 Supabase。欄位要一次想清楚，換資料庫時才不用改畫面。

## 決定

欄位寫在 [`docs/data-model.md`](../data-model.md)。幾個原則：

- **用代稱（slug）當遊戲的主鍵**：網址 `/game/kingdomino`、圖片檔名 `kingdomino_box.webp` 都用它
- **能算出來的不存**：首頁分區、遊玩時間級距、為你推薦，都從遊戲的欄位算，不另外存一份清單
- **選項存代號**：複雜度存 `casual`，畫面顯示「休閒小品」（`src/api/data/options.js`）；改文案不動資料
- **名稱依語言存**：`name: { 'zh-TW', en }`，畫面顯示目前語言的，沒有官方中文名就顯示英文；搜尋時所有名稱和別名都比對
- **同一份資料不存兩次**：我的牌桌只存「對到哪一張開放桌」，收藏只存遊戲代稱，遊戲名稱、圖片都從遊戲資料拿
- **格式集中在一個地方**：「2-4 人」「約 13 分鐘」「基礎版／10 分鐘局」都用 `src/utils/format.js`，不在元件裡各自組字串
- **篩選、排序寫成純函式**（`searchGames`、`filterTables`）：輸入資料、輸出結果，測試不用等假延遲
- 收藏、我的牌桌存在 localStorage，模擬伺服器；遊戲、排行榜寫死在 `src/api/data/`

## 考慮過的選項

- **首頁分區另外存清單**：可以人工挑選，但遊戲的欄位改了清單會忘了改，兩邊矛盾。人工指定的只有首頁主視覺（廣告版位）
- **名稱只存一個中文字串**：簡單，但之後做英文版要改資料結構
- **選項直接存中文**：資料一看就懂，但改一個字要改所有資料；換資料庫時查詢也比較麻煩

## 代價

- 每次顯示都要算一次分區和篩選。25 款遊戲沒有影響；遊戲變多、換 Supabase 時，改成在資料庫查詢
- localStorage 的資料只在這台裝置、這個瀏覽器；清掉瀏覽資料就回到預設
